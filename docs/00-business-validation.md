# Phase 0：商业验证

## 问题假设

智能合约团队在 EVM、Solana、Wasm host 和 ZK 工具链之间重复实现业务规则、测试、
SDK 与安全约束。现有语言通常绑定单一 VM；跨链框架又常把平台差异隐藏成不真实
的最小公共子集。待验证的核心价值是：用 Lean 编写一份可检查业务语义，在目标不
能保持语义时明确拒绝，在能保持时生成目标原生的 Plan 和制品。

## 目标用户与 JTBD

| Persona | Job to be done | 主要风险 |
|---|---|---|
| 多链协议工程师 | 复用状态机和不变量，同时使用各链原生制品 | 生成物覆盖不足，仍需大量手写 |
| 安全/形式化工程师 | 把业务语义与目标后端实现联系到可验证证据 | 证明只覆盖模型而非真实制品 |
| 工具链维护者 | 以明确接口持续增加目标和平台能力 | 抽象泄漏导致 backend 互相耦合 |
| ZK 应用开发者 | 同一业务规则可成为电路或 zkVM workload | 状态连续性和披露语义不明确 |

## 现有替代方案

- 分别维护 Solidity、Rust、平台 Wasm SDK 和 Noir/guest 程序。
- 以代码生成模板共享接口，但业务语义和验证仍分叉。
- 使用单一链的跨链消息协议，把执行留在原链。
- 只维护形式模型，真实目标实现由人工对照。

这些替代方案的成本、采用率和用户满意度尚未通过访谈量化，因此本文件保持
`draft`。

## 验证假设与实验

| ID | 假设 | 实验 | 通过条件 | 状态 |
|---|---|---|---|---|
| BV-01 | 团队会为减少重复实现投入迁移成本 | 访谈 10 名有两种以上目标经验的工程师 | ≥6 人确认高频问题，≥3 人愿意付费或投入试点时间 | pending |
| BV-02 | fail-closed 比“尽量编译”更有价值 | 展示 capability rejection 原型 | ≥8/10 选择明确拒绝 | pending |
| BV-03 | `program` 单入口比多个 DSL 更易理解 | 可用性测试：完成 Counter 四目标任务 | ≥8/10 无需解释顶层类别 | pending |
| BV-04 | target-owned Plan 能支持原生能力 | 专家评审四个 Phase 1 Plan schema | 无阻断性语义缺口 | pending |
| BV-05 | Lean 工具链门槛可接受 | 计时安装、首次构建和诊断修复 | 中位首次成功 ≤30 分钟 | pending |

访谈记录必须匿名化，存储参与者角色、平台经验、当前流程、失败案例、预算/试点
承诺及日期；不得只记录赞同意见。

## 手工流程

在产品化前，人工完成一次 Counter：固定语义 → 列出需求 → 对照四目标能力 → 手工
设计 Plan → 调用官方工具生成/执行制品 → 归一化 state/return/error 观察 → 记录差异。
该流程的每个判断必须转成规格规则或测试向量；未记录的人工判断不能进入编译器。

## MVP 与成功指标

MVP 只包含统一 DSL、参考语义、稳定诊断以及 Counter 的 EVM、Solana、NEAR、Noir
四目标闭环。业务成功指标：3 个外部试点、2 个非维护者可独立完成示例、目标差异
诊断一次读懂率 ≥80%。工程指标见 `NFR-*`。

## Go / No-Go

正常 Go 条件：完成 10 次访谈、≥3 个付费/明确试点承诺、手工流程和 MVP 周期估算。
若由创始人资助研究，可记录一次最长 8 周的 `founder exception`，必须注明预算、
止损日期和可证伪指标；它允许技术验证，不等同于市场验证通过。未达到条件时停止
扩展目标，只保留研究与原型。

## 当前结论

技术问题和用户假设清晰，但没有访谈、付费意向和手工流程执行证据。本阶段不能
accepted，也不能据此宣称市场需求成立。
